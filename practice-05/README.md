## Эксперимент с очередями

Прогноз по коду: A, B, C, D, E, F. Фактический вывод:

```text
A: синхронный код
B: начало async-функции
C: конец синхронного кода
D: обработчик Promise
E: продолжение после await
F: задача таймера
```

A, B, C выполняются синхронно: async-функция работает до первого await.
D и E — микрозадачи в порядке регистрации. F — задача таймера, поэтому нулевая задержка не означает немедленное выполнение.
Если удалить обработчик Promise с D, останутся A,B,C,E,F.
Добавлен собственный `Promise.resolve().then(...)` в `event-loop-extra.js`.
Прогноз: A,B,C,D,E,G,F. Фактический результат совпал:

```text
A: синхронный код
B: начало async-функции
C: конец синхронного кода
D: обработчик Promise
E: продолжение после await
G: дополнительный обработчик Promise
F: задача таймера
```

## Организация и реализация

| Модуль | Ответственность |
|---|---|
| api/server.mjs | Готовый HTTP API, фильтры, структурированные ошибки и учебные маршруты |
| src/api-client.js | URL, fetch, заголовки, тайм-аут, отмена, HTTP и разбор JSON |
| src/task-api.js | Разрешённые фильтры, ресурсы задач/категорий, проверка схемы |
| src/variant.js | Данные варианта № 2: completed=true |
| src/main.js | Консольная демонстрация и отдельная обработка 404 |

`buildUrl` принимает абсолютный HTTP(S) baseUrl без query/hash, относительный путь и обычный объект параметров.
Слеши на границах нормализуются; `URLSearchParams` кодирует значения; пропускаются только undefined/null/пустая строка,
а false и 0 сохраняются. Входные параметры не изменяются.

Фабрика проверяет baseUrl, fetchFn и положительный целый timeoutMs.
`requestJson` добавляет Accept: application/json, создаёт AbortController, объединяет внешнюю отмену и таймер,
фиксируя первую причину отмены. Таймер и обработчик внешнего сигнала освобождаются в finally.
Сигнал действует и при чтении тела. Заранее отменённый сигнал не запускает fetch.
Ответ должен быть экземпляром Response. HTTP-ошибка обрабатывается до проверки формата успешного ответа,
её status/code/details/url сохраняются даже при невалидном JSON.
204 возвращает null, остальные успешные ответы требуют JSON Content-Type и корректного JSON.
fetchFn внедряется для тестов без сети; HTTP-ошибки не перехватываются как network.

В предметном модуле id и categoryId — положительные безопасные целые; title/name — строки длиной 1–100 после trim;
completed — boolean; priority — low/medium/high. Коллекции не содержат повторяющиеся id, meta.total равен длине data.
Неверная схема отклоняется как invalid-response, без передачи повреждённых данных вызывающему коду.
Фильтры completed/priority/categoryId/q проверяются до запроса, q нормализуется через trim.
`loadInitialData` начинает getTasks и getCategories до общего await через Promise.all, возвращая tasks/categories/meta.
При отказе одной части общий Promise отклоняется; остальные запросы автоматически не отменяются.

## Отладка

Клиент ПР5 загружен как ES-модуль в Microsoft Edge и проверен с настоящим API ПР5.
Через CDP Debugger установлены точки перед fetch, после Response, перед чтением JSON и перед созданием HTTP ApiError.

Content-Type=application/json; charset=utf-8. На `/tasks/999`: status=404, ok=false,
payload.error.code=TASK_NOT_FOUND, details.id=999, итоговый kind=http.
Все шесть пауз, локальные значения и разобранные результаты: [debugging.json](./reports/debugging.json).
